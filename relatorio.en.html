Automated Recruiting Report with AI Analysis

A Python pipeline, scheduled on GitHub Actions, that reads the recruiting data published on Google Sheets, computes the indicators, builds the charts, asks the Claude API for a written analysis comparing periods and delivers two PDFs by email — an operational weekly and an executive monthly. No manual step between the data and the inbox.

01The problem

Tracking recruiting requires two different readings, at different paces. Operations needs to know, every week, what is stuck — which jobs blew the SLA, at which stage candidates are parked. Leadership needs, every month, a consolidated reading: did the funnel convert better or worse, did times go down, where did the candidates who advanced come from.

Building this by hand means opening the spreadsheet, slicing the periods, recomputing the comparisons, generating the charts, writing the text and distributing it — then repeating everything next week. It is recurring, predictable work, prone to date-slicing errors. Exactly the kind of task that should become a pipeline.

The goalDeliver two things at once to the client: the recruiting data always up to date on Google Sheets, for anyone who wants to slice it, and two ready-to-read reports — with numbers, charts and a written analysis — with nobody touching anything between source and delivery.

The separation matters for a practical reason: the job indicators (TTH, TTF, TTA, SLA) already come calculated at the source and are only consumed, never recomputed. This prevents the report and the source system from diverging — a classic error when each consumer redoes its own math.

03Automation on GitHub Actions

The ETL does not run on my machine. It runs on its own, on schedule.

  1. Scheduled trigger (schedule with cron) fires the right cadence — weekly and monthly have different windows and recipients. workflow_dispatch remains available for on-demand runs.
  2. Reproducible environment: checkout, Python setup at a pinned version and install from requirements.txt.
  3. Credentials via secrets — the API key and email credentials never enter the repository; they are injected as environment variables in the job.
  4. Pipeline execution, which generates the PDF for the matching cadence.
  5. Delivery: the PDF goes by email to the recipients and is stored as a run artifact, which gives history and allows reprocessing.

Why ActionsIt needs no server, has native scheduling, keeps the log of every run and versions the schedule itself alongside the code. For a report that runs a few times a month, it is the smallest infrastructure that solves the problem.

04What is measured

The recruiting vocabulary the report consolidates.

Indicator What it answers
TTH Time to hire — how long from application to hire.
TTF Time to fill — how long the job takes to be filled, counted from opening.
TTA Time to accept — time between offer and acceptance.
SLA Is the job within the agreed deadline? It is the alert that opens the weekly report.
Funnel Applied → screened → in process → approved → hired, with the conversion of each stage.
Sources Where candidates come from and — what matters more — the advancement rate of each channel.
Pool quality Average scores by dimension (cultural fit, reasoning, motivational…).

Every count in the period comes with the change versus the previous period — last week in the weekly, the previous closed month in the monthly. A number alone does not say whether things improved.

05The AI layer

Claude does not look at the charts: it receives the already-computed numbers and writes the reading.

This is the central decision of the AI layer. Sending images to the model to interpret introduces unnecessary error — the numbers already exist, computed deterministically. The model receives the set of metrics as text and does what it does well: prioritize what matters, connect one number to another and write in business language.

A resilient three-layer flow

  1. Cache — the analysis is indexed by a hash of the metric set. If the numbers have not changed, the text is reused: no cost and no variation in wording on each run.
  2. Claude — on a miss, the API is called with the cadence's prompt.
  3. Deterministic fallback — if the API is unavailable or there is no key, a rule-based generator writes the summary. The report never fails to go out because of the AI.

Different prompts for different readers

The weekly asks for a short, operational text that ends in action: who to chase, which job to unblock, what to do this week. The monthly asks for an executive text: context for the month, where the structural bottleneck is and prioritized recommendations. Same pipeline, same model, different instructions.

GuardrailHighlights such as "worst SLA by seniority" ignore very small samples (n < 5). Without that, a single late job would become the report's headline.

The analysis written by the model

Executive analysis · claude-sonnet-5

"Despite the growth in volume, the funnel reveals significant bottlenecks. Of 1,135 applicants, only 156 (13.7%) advanced to screening, and the largest proportional loss in the process occurs exactly at that stage, confirmed as the main chokepoint. […] The Senior seniority shows the worst SLA, even though its absolute times (TTH 18 and TTF 22 days) are lower than those of Assistant (34 and 39 days), suggesting a mismatch between deadline expectation and the real complexity of the process."

"Three priority actions are recommended. First, review and optimize the criteria and resources of the Screened stage, the funnel's main bottleneck […]. Second, investigate the causes of the low SLA for Senior jobs, adjusting contractual deadlines or reinforcing the dedication of specialized recruiters […]."

Translated from the Portuguese original generated by the pipeline.

Notice what the text does: it crosses two metrics that sit in different sections of the report — SLA by seniority and absolute times — and points out the contradiction between them. It is the kind of reading a chart alone does not deliver.

07Design decisions

  • Collection and reporting are separate automations. The Google Sheets spreadsheet is the contract between the two: one writes, the other reads. Each side evolves without breaking the other — and the data stays open to the client as a deliverable of its own, not a by-product.
  • AI never blocks delivery. Cache, then API, then rule-based fallback. The PDF goes out even without an API key.
  • Numbers computed in Python, text written by the model. Each layer does what it does best; the model does not do arithmetic.
  • Cache by metrics hash. Re-running with the same data spends no call and does not change the wording.
  • Colorblind-validated palette, with red reserved for SLA and alerts — never a decorative series color.
  • Small samples do not become headlines (n < 5 excluded from highlights).
  • Indicators consumed from the source, not recomputed — report and system do not diverge.
  • Two PDF engines. WeasyPrint by default, Playwright as an alternative when the GTK3 runtime is unavailable.
  • Secrets outside the repository, injected as GitHub Actions secrets.

Next steps

  • Slack alerts when SLA crosses a threshold, without waiting for the report cycle.
  • A historical series of KPIs so the analysis compares against the trend, not just the previous period.
  • Regression tests on the metrics, with a reference synthetic dataset.
